# 共享追番板 (shared-board) PRD

> 状态：需求方案（待评审） · 版本 v0.1 · 日期 2026-07-22
> 来源：由「资深产品经理 / 小程序架构师 / UI 交互设计师 / 二次元追番用户」四方脑爆汇总，经决策收敛。

## 0. 一句话定位（核心，务必先读）

**共享追番板不是"进度赛跑"，而是"我俩一起追到了哪、有几部能一起聊"。**

脑爆过程中，产品、设计、真实用户三方**独立地**否定了"以『谁领先、差几集』为主轴"的最初设想——那会把亲密行为变成"吵架发生器 / 记分牌 / PUA 落后方"。

因此本功能的核心价值锚定为三点，**进度差异只是实现它们的手段，不是目的**：

1. **共同话题起点** — 找到双方都看过的那条线（能一起聊到第几集、有几部能一起聊），是一起追番的社交发生点。
2. **追平 / 一起看完的仪式感** — 把追番从孤独行为变成两个人有来有回的共同经历。
3. **陪伴感** — 你追番的每一步，有一个特定的人在乎、在看、会回应。

> 基调：**陪伴，不是排名。** 所有 UI、文案、激励机制都服从这一条。
>
> **注（2026-07-23 修订）**：原三大价值含"防剧透边界"，评审发现其在实现中从未落地（对方精确集数一直显示、只在措辞层糊一下"领先不少"，自相矛盾）。经决策**砍掉防剧透**：进度信息全透明，措辞统一精确，配色仍走蓝不走红以守"陪伴不排名"。§8.3 原防剧透章节作废，见该节说明。

## 1. 背景与问题

现有「番剧追踪」(`anime-checklist`) 是纯本地单人版：`{ id, name, watched, createTime }` 存 `wx.setStorageSync`，只能标记"已看完/未看"。它是一个人的记账本，追番的每一步没有人在乎、在看、会回应。

「共享追番板」是它的多人升级版：两个人各自打开同一个板，看到同一份番单，各自维护"看到第几集"的进度，界面表现双方进度的异同。

**这不是加一个页面，而是项目首次引入后端底座**（详见 §7.1）。

## 2. 目标用户与场景

| 场景 | 谁 | 痛点 | 爽点 |
|------|-----|------|------|
| **A. 情侣云一起看** | 异地/错峰的小情侣，说好一起追一部新番 | 微信里反复问"你看到第几集了""别往前看等我"，靠聊天对进度，累且易剧透 | 一眼看清安全话题聊到哪、追平时一起解锁吐槽 |
| **B. 基友补番陪跑** | 两个死宅，把一堆番塞进共享片单 | 个人番单是孤岛，肝了一整季没人知道，没正反馈 | "都追到 E8 了，能聊了"的共同进度感（**不是**攀比谁快） |
| **C. 安利与被安利** | A 硬安利 B 入坑某部番 | 安利完就失联，B 看没看、到哪、弃没弃全不知道 | A 看到 B 进度爬升、精准补刀"撑住，E6 有高潮" |

> 三个场景的"催更"情绪完全不同（等我 / 一起追 / 别弃坑），催更文案不能一个模子，需随双方进度关系动态变（详见 §5.3、§8.3）。

## 3. 核心价值主张

> **个人追番是记账，共享追番板是一起追。**

区别于个人版的杀手锏不是"云同步"（那是手段），而是：**你追番的每一步，有一个特定的人在乎、在看、会回应，且你们始终知道彼此能安全聊到哪。**

## 4. 功能范围（MoSCoW）

> 已定决策：**① 固定 2 人配对 · ② MVP 手动输入番名（后续接 Bangumi）· ③ MVP 不做 watch 实时，用"打开即最新 + 下拉刷新"。**

### Must（MVP，小而完整、能上线）

- **建板 + 2 人配对**：一方建板，微信分享卡片拉另一方入板（吃微信社交链，不自建邀请码，详见 §8.1）。
- **共享番单增/改/删**：两人都能操作，反映到对方。番剧条目是**共享单一实体**，从根上消除"两人番名对不齐"的问题（详见 §6.1）。
- **每人独立维护进度**：番单共享，"我看到第几集"每人一份，互不覆盖。
- **进度状态机（二维）**：主状态 `想看 / 在追 / 追平待更 / 暂缓 / 看完 / 弃番` + 当前集数。少了"追平待更""弃番"就脱离真实追番行为。
- **同轴双头像对比视图**：核心门面页，两人头像跑在同一条集数轴上（详见 §9）。
- **"打开即最新 + 下拉刷新"**：进板拉取最新数据，页面内可手动刷新。**不做 watch 实时**。

### Should（紧随 MVP）

- **按集解锁的短评/评分**（真实用户最想要的钩子）：双方都看过 E5，E5 的短评/评分才对彼此解锁，像开盲盒。这是"一起追番"的灵魂。
- **催更 / 戳一下**：受小程序推送能力限制，先做"板内红点 + 下次打开可见"，订阅消息推送单独评估授权率（详见 §7.3 风险）。
- ~~**防剧透模式**~~：**已砍**（2026-07-23）。原设想领先幅度模糊化 / 落后方默认折叠对方精确集数，实现中从未落地且自相矛盾，决策放弃，进度信息全透明。见 §8.3。
- **从个人番单导入到共享板**：复用已有本地 `anime-checklist` 数据当冷启动弹药，避免空板起步。

### Could（看数据再说）

- **接 Bangumi API**：搜索选番、自动补全番名/封面/**总集数**，一部番一个唯一 ID，别名/分季挂 ID 下。这是进度条分母的隐藏依赖。
- **"等我一起看"约定**：标一句"这集想跟你一起看，别先看"，把进度差从竞争扭成约定。
- **进度里程碑动效**：追平/反超/双通关高光（复用现有三阶段动画基因）。
- **年度共同追番报告**。

### Won't（本期明确不做）

- 多人板（>2 人）— 已定 2 人配对是唯一形态。
- 番剧正片播放 / 资源链接 — 是工具不是视频站，碰版权红线。
- 公开社区 / 陌生人匹配 — 熟人小圈子，不做广场。
- 弹幕 / IM 聊天 — 微信本身就是 IM，不重造。
- 真·实时 watch（MVP 阶段）— 见 §7.2 决策理由。

## 5. 关键产品决策

### 5.1 定位转向：进度差异是手段不是目的

见 §0。落地约束：
- 布局用"同轴共进式"而非"左右对峙式"，避免记分牌对抗感。
- 措辞给正向主语：不说"你落后 4 集"，说"TA 领先 4 集"或"还差 4 集追上"。
- 绿色只奖励里程碑（追平/看完），**不常驻表示领先方**（否则又变回输赢色）。

### 5.2 进度表达：状态 + 集数二维

- **主状态（枚举）**：`想看 / 在追 / 追平待更 / 暂缓 / 看完 / 弃番`。状态本身是社交信号（"你居然弃了？！"）。
- **当前集数**：仅"在追/追平待更"下有意义。
- **追番 vs 补番语义不同**：日更番"落后"= 没跟上最新话（催更成立）；补番"落后"只是没空刷（催更招烦）。番剧条目带 `放送中 / 已完结` 标记，催更文案据此分化。

### 5.3 催更：动态文案 + 冷却

- 文案随双方进度关系变：领先方看到"等等 TA"，落后方收到"TA 在等你一起追"。
- **同一部番对同一人催更设冷却**（如 4 小时一次），冷却时长走配置层不硬编码。
- MVP 只做"板内红点 + 下次打开可见"，即时推送受小程序订阅消息限制（§7.3）。

### 5.4 生命周期终点（口碑生死线）

- **允许一个人加入多个板**（和对象一个、和基友一个）。首页需"我的板"列表入口。若限死 1 个，"想和不同人开不同板"直接卡死。
- **退出/解散**：情侣分手、基友闹掰要能干净退出。任一方可退出，板对双方冻结为**只读归档**，不物理删除对方数据。**退出流程不尴尬、不挽留、不满屏共同回忆**——这是情侣向功能的头号坟墓，决定用户敢不敢用。

### 5.5 筹备态：单人可先用（2026-07-22 会议决策）

背景：原实现「配对成功才显示番单」，导致建板后、对方加入前用户停在等待页啥也干不了（冷启动硬伤）。经产品 + 真实用户双视角对齐，决定**支持单人先用**。

**核心心智纠偏（两方独立强调）**：这不是「单人模式」，是「**筹备态 / 候场室**」——一张摆了两副餐具、只坐了一个人的桌子。**绝不能把它做成完整的单人产品**，否则会得到一个更慢更重、还打不过 B 站/Bangumi 的第二个番单工具，稀释掉「共享」这个唯一命根。团队术语统一用「筹备态」。

**筹备态定位**：功能可与个人版 `anime-checklist` 重叠，但性质是**过渡态、他者指向**——「我俩的番单，TA 还没来」。每加一部番的心理动作是「给 TA 攒话题、攒共同片单」，视觉上**始终有一把空椅子（虚位头像）在等人**。

**筹备态功能清单**：
- ✅ 保留：加番、改自己进度/状态、改番剧共享信息、软删除
- ⚠️ 中性化：分区名去掉关系词（用「在追/想看/看完」而非「一起追」）
- 🚫 隐藏（非灰置）：对方游标、进度对比、差值文案、催更、「N 部能一起聊」、追平/反超/同步仪式
- 🎣 唯一保留的钩子：第二个头像位显示**虚位 + 「邀请 TA」**（是诱饵不是伤口，区别于灰置禁用态）

**对方加入后的过渡**（配对后 case）：
- 对方对所有番的初始进度 = **「还没翻牌」（未设，非"想看"非"E0"）**——数据模型天然成立（progress 无对方 openid key），不替对方表态/撒谎。翻牌永不强制、不 gate 任何东西。
- **入伙交接时刻**（新设计缺口，MVP 可简化，动效放 Should）：对方加入时看到「XX 已经为你俩攒了 N 部番」片单速览。建板方侧要有「TA 加入了」的异步通知/红点兑现。

**防稀释（MVP 轻量，精细机制放 Should）**：MVP 只做「隐藏双人 UI + 留空椅 + 常驻邀请入口」。将来 Should 再做「双人功能上锁 teaser」「情绪峰值轻推邀请」「最爽多巴胺（追平/短评解锁/一起看完）锁在配对后」。**审视风险**：单人太好用会自我蚕食邀请动机，指标口径需分开——北极星是**配对率 / 配对时长 / 配对后留存**，单人板不算成功指标（Should 埋点）。

## 6. 数据模型设计

### 6.1 核心难点：共享条目 + 私有进度

诉求里最硬的一条：**番剧条目两人共享（一人加两人都看到），但进度各自独立（互不覆盖）**。这是"共享实体 + 私有关联状态"。

选型：**进度以 openid 为 key 内嵌进条目子文档**，用"定位到子字段的原子更新"化解覆盖冲突。2 人番单量级最多几百条，无需把进度拆独立集合（那是为想象中的规模过度设计）。

> 这个模型顺带消解了真实用户担心的"番名对不齐"：条目是**单一共享实体**，一人加、另一人直接在同一条上追进度，不存在各写各名字的问题。遗留的"分季/剧场版命名"困扰留给后续接 Bangumi。

### 6.2 集合结构

集合名、人数上限等一律走配置常量，不硬编码：

```js
// packageFeatures/utils/shared-board/config.js（前端）
// cloudfunctions 侧同源常量
const COLLECTION = {
  BOARD: 'shared_boards',
  ITEM:  'shared_board_items',
};
const BOARD_MEMBER_LIMIT = 2;   // 人数上限（配置，不写死数字 2）
const PROGRESS_STATUS = ['want', 'watching', 'caught_up', 'paused', 'done', 'dropped'];
```

**集合一：`shared_boards`（板 + 成员，合一）**

```js
{
  _id: 'board_xxx',              // 板 ID，分享卡片携带
  _openid: '<创建者 openid>',    // 云开发自动写入，标记建板人
  name: '我俩的番单',
  members: [                     // 成员数组，长度上限 = BOARD_MEMBER_LIMIT
    { openid: 'oABC', nickname: '小高', avatar: 'https://…', role: 'owner', joinAt: 168… },
    { openid: 'oDEF', nickname: '小王', avatar: 'https://…', role: 'guest', joinAt: 168… }
  ],
  memberOpenids: ['oABC', 'oDEF'], // 冗余扁平数组，供权限规则 includes 判断
  status: 'active',              // active / full / archived
  createTime, updateTime,
}
```

**集合二：`shared_board_items`（共享条目 + 私有进度）**

```js
{
  _id: 'item_xxx',
  boardId: 'board_xxx',          // 外键，watch/query 按它过滤
  name: '葬送的芙莉莲',           // 番名（共享，谁都能改）
  totalEp: 28,                   // 总集数，可空（MVP 手动输入常为空）
  airStatus: 'finished',         // airing 放送中 / finished 已完结（影响催更语义）
  cover: '',                     // 封面，可空
  addBy: 'oABC',                 // 谁加的（审计，不参与权限）
  progress: {                    // ★以 openid 为 key，天然按人隔离
    'oABC': { ep: 12, status: 'watching', updateTime: 168… },
    'oDEF': { ep: 5,  status: 'watching', updateTime: 168… },
  },
  // ★排序各存各的（决策 2026-07-22）：番单内容共享，展示顺序每人一份，
  //   从根上消灭排序冲突。渲染时按当前用户 openid 取值。
  sortOrder: { 'oABC': 1000, 'oDEF': 1200 },
  // ★软删除（决策 2026-07-22）：deleteItem 只标记不物理删，
  //   避免 A 删番导致 B 进度凭空蒸发；对方可一键恢复。
  deleted: false,                // 是否已移出番单
  deletedBy: '',                 // 谁移出的（openid），供"A 移出了《X》"提示
  deletedAt: null,               // 移出时间
  createTime, updateTime,
}
```

**为什么既实时又不覆盖**：
- 共享性：`name/totalEp/cover` 是顶层字段，一处改两人同步。
- 私有性：进度锁在 `progress.<自己 openid>` 子键，排序锁在 `sortOrder.<自己 openid>` 子键。A 更新时**只定位写 `progress.oABC.ep` / `sortOrder.oABC` 这些子字段**，物理上碰不到 oDEF 的。绝不"读整条→改→写回"（那才覆盖）。
- 软删除：`deleted=true` 而非物理删，两端仍能看到并恢复，进度数据不丢失。

### 6.3 外部数据源可行性调研（2026-07-22 留档）

调研背景：为「番名自动补全、封面、总集数」评估可接入的番剧元数据源。**结论：MVP 无可用的理想源，手动输入是当下唯一可行方案；数据层按「来源无关」设计。**

| 数据源 | 国内可访问 | API 开放度 | 商用限制 | 结论 |
|--------|-----------|-----------|---------|------|
| **弹弹play** `api.dandanplay.net` | ✅ 国内服务 | ✅ 正式开放平台（AppId/AppSecret 签名） | ⚠️ **明确禁止未授权商用**，免费个人应用可申请 | 🥇 将来第一候选 |
| B站番剧 `api.bilibili.com` | ✅ 最稳 | ❌ 非官方，民间逆向 | ❌ 无授权、条款灰色 | 数据全但灰色，不选 |
| 豆瓣 | ✅ | ❌ 官方 API 已关停 | — | 淘汰 |
| ~~Bangumi~~ `api.bgm.tv` | ❌ **2026-05 起全线被墙** | ✅ | 非商用免费 | 淘汰 |
| ~~TMDB~~ `api.themoviedb.org` | ❌ **国内被封锁** | ✅ | 非商用免费 | 淘汰 |

**关键约束（供后续接入时注意）：**
- **云函数在境内（腾讯云），够不着被墙的境外域名**（Bangumi/TMDB），云函数只能绕微信域名白名单，绕不过国家级封锁。
- **弹弹play 2026-06-25 起启用配额分级 + 重接口自动限流，强制要求缓存**（建议 2-6 小时）——反向印证「元数据必须落自己云数据库缓存，不实时打第三方」的架构方向。
- **没有一个源保证长期可用**（被墙/限流/改接口/条款皆可能变）。因此**不赌单一源**。

**架构决策：数据层字段设计为「来源无关」** —— `cover / totalEp / alias / airStatus` 谁填都行（手动、将来某个可用源、用户自填），**不绑定任何源的专有 ID 作为主键或外键**。将来接外部源时做成**独立可替换的「数据源适配层」**，换源只改适配层，不动数据模型与页面。**MVP 不预先实现任何源接入、不申请 AppId、不写鉴权签名**（避免为不确定的未来过度设计）。

## 7. 技术架构

### 7.1 云开发接入影响（诚实评估：这是架构升级）

项目现状（已核实代码）：`app.js` **无 `wx.cloud.init`**；`project.config.json` **无 `cloudfunctionRoot`**、`appid=""`；根目录**无 `cloudfunctions/`**；现有 4 个功能对 `wx.cloud` 零引用。这是从 0 到 1 接入。

| 改动项 | 内容 | 阻塞级 |
|--------|------|--------|
| **真实 AppID** | `appid=""`，云开发强依赖注册过的 AppID，测试号无法开通云环境。**第一步就卡死的前置项** | 🔴 阻塞 |
| **开通云环境** | 开发者工具「云开发」控制台开通，拿环境 ID | 🔴 阻塞 |
| **app.js 初始化** | `onLaunch` 加 `wx.cloud.init({ env, traceUser: true })` | 🟡 必改 |
| **project.config.json** | 加 `"cloudfunctionRoot": "cloudfunctions/"` | 🟡 必改 |
| **基础库版本** | `wx.cloud` 需 ≥2.2.3，`db.watch` 需 ≥2.8.1，当前 2.20.1 满足 | 🟢 已满足 |

- **环境 ID 不硬编码**：抽到 `miniprogram/config/cloud.js`，业务代码只认符号名。
- **对现有功能零影响**：`wx.cloud.init` 只在启动执行一次，其他功能不碰云 API。
- **主包体积几乎无影响**：`wx.cloud` 是内置 API 不占包体积；共享板页面放分包；**本方案不新增 npm 包**（TDesign 已在用），故**无需重新构建 npm**——除非用到当前未引入的 TDesign 组件。
- **README 定性变更**：`docs/README.md` "纯原生，无云开发依赖"届时改写为"原生 + 云开发混合"。

### 7.2 同步方案：MVP 不做 watch

**决策：MVP 用"打开即拉取 + 页面内下拉刷新"，watch 放 Should。** 理由：
- 2 人板不需要毫秒级实时，为想象中的实时性烧 watch 配额是过度设计（踩项目铁律）。
- 真实用户反馈实时会有"被监控"的压迫感，进度更新反而应有时间上的延迟感（非即时，指刷新节奏，与已砍的集数防剧透无关）。
- 用数据验证真有"同时在线共看"需求后再上 watch，届时按分集合监听（`where(boardId)` 收窄）+ `onHide` 关 / `onShow` 重建 + 退避重连兜底。

### 7.3 身份与配对

- **免登录识别你我**：云函数 `cloud.getWXContext().OPENID` 拿可信 openid（客户端伪造不了）。前端 `onLoad` 缓存自己 openid，渲染时 key 等于自己的是"我"，另一个是"TA"。
- **配对流程**：建板方 `createBoard` → 分享卡片 path 带 `boardId` → 对方点开 `onLoad` 解析 → 云函数 `joinBoard` 校验（板存在/未满/去重）→ 占第二坑。
- **安全**（全在云函数，客户端说了不算）：
  - 所有身份写入 openid 一律取自 `getWXContext`，忽略客户端传的 openid → **防伪造**。
  - `joinBoard` 校验 `members.length >= BOARD_MEMBER_LIMIT` → **防第三人乱入**。
  - 并发加入用**条件更新**（人数<上限作为更新条件），数据库原子性保证只有一个写成功 → **防并发导致 3 人**。

### 7.4 权限与安全规则

网络暴露数据，默认收紧。原则：**读走权限规则（限成员），写全走云函数（严格校验）**。

```jsonc
// shared_boards 权限规则
// ⚠️ 微信安全规则不支持 .includes()，数组成员判断只能用 in（已核实官方文档）
{ "read": "auth.openid in doc.memberOpenids", "write": false }

// shared_board_items 权限规则（推荐：把 memberOpenids 冗余到 item，免 get() 读配额）
{ "read": "auth.openid in doc.memberOpenids", "write": false }
// 备选（反查 board，代价是每条 item 一次 get 读 + 查询必带 where(boardId)）：
// { "read": "auth.openid in get(`database.shared_boards.${doc.boardId}`).memberOpenids", "write": false }
```

写为什么全走云函数：数据库权限规则是**文档级**权限，**无法表达"只准改 progress 里自己那个子键"**这种字段级粒度（已核实官方文档）。进度私有性只能靠云函数用 `getWXContext` 取可信 openid + 动态 key `progress.${OPENID}` 定位子字段更新来保证。这是官方认证的"读走规则、写走云函数"标准分层。详细设计见 [`shared-board-data.md`](shared-board-data.md)。

**云函数清单**：`getMyOpenid` / `createBoard` / `joinBoard` / `addItem` / `updateProgress`（只改自己子键、ep 合法性校验）/ `updateItem` / `deleteItem`（软删除）。

### 7.5 落地到项目结构

```

  shared-board.{js,json,wxml,wxss}                 # 亮/暗双模式适配
miniprogram/packageFeatures/utils/shared-board/    # 纯逻辑（可 Node 测试）
  config.js        # 集合名/人数上限/状态枚举/催更冷却等常量

cloudfunctions/    # 云函数（不进小程序包体积）
tests/shared-board.test.js                         # 对齐现有零依赖 Node 测试
```

- `app.json` 分包 pages 追加 `"pages/shared-board/shared-board"`；首页 `features` 数组加一项（已是配置驱动）。
- **纯对比逻辑抽 `transform.js`**（对齐 mahjong/worldcup 可测约定）：`buildProgressPair(item, myOpenid, peerOpenid)` 输出 `{ mine, peer, diff, lead, minePercent, peerPercent }`，不依赖 `wx.*`，可在 Node 测"我领先/对方领先/持平/无总集数/进度回退"等分支。

- `package.json` 的 `test` 脚本追加 `&& node tests/shared-board.test.js`。

## 8. 关键产品/交互决策补充

### 8.1 配对建板：分享卡片即加入（不自建邀请码 UI，但校验省不掉）

微信分享卡片本质是**广播**（可转发、可甩群），"谁点开谁加入"会被第三者抢坑。方案：卡片 path 带 `boardId`，云函数 `joinBoard` 校验板未满 + 成员去重后才占坑。**"不自建邀请码"只是不让用户手输，token/占位/防抢坑/过期逻辑一个不能少**，别低估后端复杂度。

### 8.2 番单增删冲突

- **删除做软删除/归档**，绝不物理硬删（A 删了 B 在追的番会让 B 进度凭空蒸发）。对方看到"A 把《X》移出了番单"，可一键恢复。
- **排序各存各的**（内容共享、展示顺序每人一份），从根上消灭排序冲突。
- **字段权限分离**：进度/状态/短评是私有字段（只本人能改自己）；番名/封面/是否在单里是共享字段（两人都能改）。

### 8.3 剧透处理 —— 已作废（2026-07-23 决策砍掉防剧透）

> **本节整体作废，保留作决策留档。**
>
> 原设想（领先幅度模糊化、落后方默认折叠精确集数、短评打码、每部番开关）在四方评审时被发现**从未真正落地**：代码里对方精确集数（`我 E8 · TA E12`）一直无条件显示，所谓模糊档只在措辞层把"领先 X 集"糊成"领先不少"——用户一减就知道差几集，是欲盖弥彰的空壳，且与"精确集数已显示"自相矛盾。
>
> **决策：砍掉防剧透，进度信息全透明。** 理由：① 熟人 2 人板，很多情侣本就故意对进度、过度防剧透是自作多情；② 半吊子实现比不做更糟（招牌与货不符）；③ 省下的复杂度投给真正的卖点（共同话题、追平仪式感）。
>
> **连带改动**：`transform.js` 去掉 `gapMode` 的 `blurred` 档，领先措辞统一精确（"TA 领先 X 集 / TA 还差 X 集追上"），配色仍走蓝不走红以守"陪伴不排名"；`config.js` 删 `VIEW.BLUR_GAP`。`gapMode` 的 `break` 档（超大 gap 的轴断裂视觉）与剧透无关，是纯视觉降级，保留。

## 9. UI 交互设计

> 📐 **本节为脑爆原始素材。完整可实现的设计规格（逐页线框、组件映射、集数轴自绘规格、动效表、亮暗配色、字段交叉检查）见独立文档 [`shared-board-ui.md`](shared-board-ui.md)。**
> 该文档在交叉检查中发现并已修正 PRD 两处内部冲突（2026-07-22）：① 排序改为「各存各的」`sortOrder.<openid>`；② 补软删除字段 `deleted/deletedBy/deletedAt`。均已反映到 §6.2。

### 9.1 核心门面：同轴双头像共进式（推荐方案）

两个头像作为两个"跑者"跑在**同一条集数轴**上，差距=两头像物理间距，不需读数字大脑就能感知。

**有分母（已知总集数）：**

```
┌──────────────────────────────┐
│  葬送的芙莉莲                  [在追] ⋯ │
│  1 ──●━━━━━━◐──────────── 28      │  ← 同一条轴，两头像=两游标
│       我(E8)  TA(E12)                    │
│       └─ 相差 4 集 ─┘                    │
│                    [ 我看完这集 +1 ]     │
└──────────────────────────┘
```

**无分母（MVP 常态，只有相对领先）：** 右端以"跑在前面的人"为锚点，用 mask 渐隐暗示"未完待续、没有终点"：

```
┌──────────────────────────────┐
│  葬送的芙莉莲                  [在追] ⋯ │
│     ……──●━━━━━━◐                  │  ← 右侧渐隐，无右边界
│         我(E8)   TA(E12·最新)            │
│              相差 4 集                    │
│                    [ 我看完这集 +1 ]     │
└──────────────────────────┘
```

**列表页紧凑版**（每番一行）：

```
┌────────────────────────────┐
│ 葬送的芙莉莲            [在追]        │
│ ●━━━━◐····  我8·TA12·TA领先4        │
├──────────────────────────┤
│ 咒术回战              [追平!]        │
│ ····◉····  我24·TA24·同步            │  ◉=两头像重叠
├──────────────────────────┤
│ 迷宫饭                [看完]        │
│ ━━━━━━●◐  我12·TA12·都看完 🎉     │
└──────────────────────────┘
```

**备选方案（左右分栏对峙式）降级为单番详情展开态**：清晰但窄屏挤（每栏仅~150pt）、双进度条需二次比对、对抗感强，不适合做列表主视图。

### 9.2 进度差异视觉语言

- **三层编码**：谁领先=位置（谁靠右）；领先多少=头像间距+文字兜底（`--td-text-color-secondary` 小字）；是否追平=头像重叠 `◉` + 状态标签变"同步"。
- **禁用红色表达落后**（红=错误/危险，落后不是错）。落后方游标正常显示不降饱和不变灰（变灰=隐性羞辱）。
- **差距过大**（如 E2 vs E24）轴中段画断裂波浪 `∿` + "相差 22 集"，不做等比拉伸。
- **远端进度变更也走同一条 0.3s 回弹动画**滑过去，让"TA 刚更新"有物理存在感，别瞬移（像卡了）。

### 9.3 仪式感（复用现有三阶段动画基因）

复用 `anime-checklist.wxss` 的 `itemGlow / cardFlash / bounceIn / bounceOut` 与回弹 `cubic-bezier`：

- **追平瞬间**：两头像向中点滑动靠拢→"撞上"触发 `itemGlow` 发光→`cardFlash` + 冒出"同步啦"徽章 + 状态标签翻转"追平!"。配 `wx.vibrateShort`。
- **反超瞬间**：自己游标超过对方时拖一条品牌色拖影，对方游标**不做任何负面动效**——只奖励前进，不惩罚被超。

### 9.4 交互流

- **配对建板**：① 空板 `t-empty`+「邀请 TA」→ ② 微信分享卡片 → ③ 等待态用**虚位头像呼吸动效**（非 loading 转圈，呼吸=在等一个人）→ ④ 对方加入瞬间虚位头像实体化 `bounceIn` + `t-message`「TA 来了 🎬」。
- **更新进度**：主手势 `+1`（90% 场景是"刚看完一集"，最快）；点集数数字弹 `t-popup`+`t-picker` 滚轮处理跳集补录；**不做滑动改游标**（窄屏难精确、误触高）。
- **催更**：`t-button size="extra-small"`；发起方即时轻反馈（摇一摇+toast），接收方推送+进板"被戳"动效（`bounceOut` 摇摆）+`t-badge` 红点；冷却态置灰防骚扰。

### 9.5 状态与边界

| 状态 | 呈现 |
|------|------|
| 空板 | `t-empty` + 「邀请 TA」 |
| 等待对方加入 | 虚位头像呼吸动效，文案「链接已发出，等 TA 点开」 |
| 对方还没设进度 | **不显示 0/0 空进度条**，显示「TA 还没翻牌」拟人文案 |
| 对方弃番 | 中性灰 `--td-text-color-placeholder` + 停在原地小旗标「TA 在 E6 下车了」，不消失不变红，留「戳 TA 回来」CTA |
| 总集数未知 | 相对轴 + 右端渐隐，不硬造分母不显示百分比 |
| 两人都看完 | 双头像重叠终点 `◉` + 🎉 + `itemGlow` 一次，归档到「一起追完的番」 |

### 9.6 亮/暗双模式配色（严格走 TDesign CSS 变量）

| 语义 | 变量 |
|------|------|
| 卡片底 | `--td-bg-color-container` |
| 轴底轨（未走） | `--td-bg-color-component` |
| 已走区间/领先前沿 | `--td-brand-color` |

| 追平/看完成就 | `--td-success-color`（**仅正向里程碑，不常驻表示领先**） |
| 辅助/差值文字 | `--td-text-color-secondary` |
| ~~落后~~ | ~~`--td-error-color`~~ **禁用** |

> **注意洞**：现有 `itemGlow` 里 `rgba(0,82,217,0.2)` 是写死值，暗模式下辉光偏暗看不清，复用时需抽成变量或暗模式提高 alpha（如 0.35）。

## 11. MVP 收敛（一句话）

**做「一份共享番单 + 同轴双头像对比页 + 进度状态机 + 一个催更红点」，进度先不带分母、同步先不上 watch、番名先手动输入。** 把"同轴对比页"这一个门面打磨到位，其余往后放——这是验证"两人黏性"核心假设的最小切片。

真实用户的判断作为北极星：**核心价值是"我俩现在能安全聊到第几集"，不是"谁快"。** 命名对齐与"追平待更/弃番"状态是能不能用的**及格线**；按集解锁的剧透安全短评区是让人**天天想开**的钩子。~~分手/绝交的干净退出~~ 曾被列为生死线，**2026-07-27 决策砍掉，坚决不做**（见 §13 甲）。
